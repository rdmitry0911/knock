# Knock Control 3

Knock Control предоставляет управляемый аварийный доступ к чувствительным сервисам, которые в штатном режиме закрыты от публичного интернета. Сервер создаёт секреты и выдаёт клиентам QR и JSON-профили. Каждый секрет имеет собственные настройки и ограничения; один профиль можно использовать на нескольких устройствах с разными внешними IPv4. Порядок работы: **импорт один раз → ON → работа с сервисом**. OFF сразу снимает разрешение своего IP. Есть расширения Chrome/Firefox и веб-приложение для мобильных браузеров.

- **Вкл** — отправить TOTP-последовательность и подписанное подтверждение, разрешить TCP-трафик от своего IPv4.
- **Выкл** — немедленно снять разрешение своего профиля/IP. Защищённый трафик, включая установленное соединение, перестаёт пропускаться, если его не разрешает другой профиль.
- **Автоматическое отключение** — после заданного времени **без трафика к защищённому сервису**. Активное соединение продлевает разрешение; шум в knock-диапазоне и обращения к API не продлевают его.
- **Настройки** — изменить только профиль своего секрета и только в пределах политики, выданной администратором.

Служба knockd продолжает работать и принимать новые запросы, когда все клиенты нажали «Выкл». Клиентские кнопки не останавливают общую службу. Несколько разных секретов могут работать одновременно.

## Мотивация: аварийный доступ при недоступном VPN

Механизм может служить заранее подготовленным администратором **аварийным входом («бэкдором»)** в трудных случаях, когда основной способ доступа, например VPN, не работает: из-за сбоя VPN-службы, проблем маршрутизации, настроек клиента или недоступности VPN-протокола в текущей сети. Через этот независимый от VPN канал можно временно получить доступ к SSH, RDP, интерфейсам администрирования и другим чувствительным TCP-сервисам, которые в обычном режиме недоступны из публичного интернета, восстановить основной доступ и затем закрыть аварийный вход кнопкой OFF.

Авторизованный клиент подтверждает владение выданным сервером секретом с помощью TOTP-последовательности и подписанного подтверждения. Сервер разрешает выбранные порты только для IPv4 этого клиента. Пока клиент работает с сервисом, разрешение продлевается; после простоя оно автоматически истекает. Остальные адреса продолжают блокироваться. Доступ к самому сервису проходит его обычную аутентификацию.

Для аварийного использования установите и настройте механизм заранее, сохраните профиль на клиенте и проверьте доступ из внешней сети. Сервер и выбранный транспорт управления должны оставаться достижимыми: TCP/UDP-knocks для настольного режима либо HTTPS API для браузерного. Тогда для открытия порта не требуется работающий VPN или уже открытый SSH-сеанс. Полная недоступность сервера или блокировка всех необходимых сетевых путей делает этот канал недоступным тоже.

Для настольного ON/OFF без доступного API клиенту нужен актуальный внешний IPv4: заранее сохранённый или введённый вручную в настройках. Обычно помощник определяет его через API автоматически. После смены внешнего адреса сохранённый IP нужно обновить.

В текущей реализации защищаются TCP-сервисы самого хоста, принимающие подключения на его внешнем IPv4 или `0.0.0.0`, с доступом, закрытым правилами firewall. Сервисы, слушающие только адрес VPN или `localhost`, потребуют дополнительной маршрутизации или прокси.

## Требования

Сервер: Linux с systemd, libpcap, OpenSSL, iptables и ipset/ядро с модулем SET. Мобильный клиент: современный браузер с HTTPS/Web Crypto; для расширения Firefox Android — 142+. Клиент HTTPS работает без Python и локального помощника. Настольный режим с настоящими TCP/UDP-knocks требует Linux, Python 3 и обычную установку Chrome/Chromium/Edge или Firefox 142+; Snap/Flatpak требуют отдельной настройки Native Messaging. IPv6, Docker FORWARD и облачные firewall требуют отдельной интеграции.

## 1. Установка на сервере

Скопируйте проект на сервер и из его каталога выполните:

```sh
sudo apt-get install build-essential libpcap-dev libssl-dev openssl python3 iptables ipset
./scripts/build.sh
sudo ./scripts/install-server.sh
```

Первичная настройка выполняется администратором на сервере. SSH может использоваться администратором для установки и выдачи файлов, но клиентам SSH-аккаунт и sudo не нужны.

Инициализируйте сервер, заменив адрес и интерфейс:

```sh
sudo /usr/local/sbin/knock-control init \
  --public-host server.example.com \
  --interface ens3 \
  --api-port 8443
```

Команда создаёт базу, TLS-ключ и сертификат. Она отказывается перезаписывать существующую базу. Адресом может быть публичный IPv4 или домен. Посмотреть интерфейсы можно через `ip -br -4 addr`. При необходимости API можно слушать на конкретном IPv4 через `--bind`; адрес в `--public-host` должен вести на доступный клиенту слушающий интерфейс.

Для телефонов и расширений без помощника установите **сертификат HTTPS, которому доверяет браузер**, на имя из `--public-host`. Например, после получения сертификата у вашего CA:

```sh
sudo knock-control tls \
  --cert /etc/letsencrypt/live/server.example.com/fullchain.pem \
  --key /etc/letsencrypt/live/server.example.com/privkey.pem
```

Сертификат нужно получить отдельно; команда проверяет пару и устанавливает её в API. Сервер должен быть доступен по IPv4. После продления сертификата повторите `tls`; у настольных клиентов с закреплённым отпечатком потребуется повторный экспорт/импорт профиля. Для браузерного клиента действует обычное доверие CA и имя узла, а не pin из JSON. Самоподписанный сертификат из `init` подходит для настольного помощника; мобильный импорт/камера и веб-приложение требуют доверенного HTTPS. Отключать проверку сертификата в рабочем браузере не нужно.

Инициализация и выдача первых файлов **до активации** не включают защиту портов. Это позволяет сначала передать файлы клиентам, а затем включить правила без потери возможности настроить клиент.

## 2. Выдача отдельных секретов

Например, выдать Alice доступ к порту 443 с возможностью выбирать 443/8444 и менять простой до часа:

```sh
sudo /usr/local/sbin/knock-control issue \
  --name Alice \
  --ports 443 \
  --allowed-ports 443,8444 \
  --idle-timeout 600 \
  --max-idle-timeout 3600 \
  --out /root/alice.knock.json \
  --qr-out /root/alice.knock.png
```

Выдать Bob другой секрет и другие настройки:

```sh
sudo /usr/local/sbin/knock-control issue \
  --name Bob \
  --ports 2222 \
  --idle-timeout 120 \
  --max-idle-timeout 600 \
  --out /root/bob.knock.json
```

QR можно создать повторно для уже выданного профиля:

```sh
sudo knock-control qr PROFILE_ID --out /root/client.png
sudo knock-control qr PROFILE_ID --out /root/client.svg
sudo knock-control qr PROFILE_ID --terminal
```

Генерация и распознавание QR выполняются локально, без внешних QR-сервисов. PNG/SVG/JSON создаются с правами 0600. QR содержит полный профиль, включая секрет: передавайте его только адресату. Ссылка имеет вид `https://server:8443/app/#import=kc2_…`; секрет находится во фрагменте, который браузер не отправляет HTTP-серверу. Приложение сразу удаляет фрагмент из адреса и истории. Не публикуйте этот QR. QR `otpauth://` от Google Authenticator не заменяет полный профиль подключения.

Без `--allowed-ports` разрешённый список совпадает с `--ports`. `--native-only` запрещает браузерный ON/OFF для данного секрета: остаётся настоящий TCP/UDP-клиент. По умолчанию разрешены оба транспорта. Флаг `--fixed-settings` запрещает клиенту менять настройки, сохраняя кнопки Вкл/Выкл. Каждый вызов `issue` генерирует на сервере новый случайный Base32-секрет 160 бит, ID и отдельный диапазон knock-портов. Клиент не задаёт секрет при выдаче и не может создавать новые профили через API.

Доступные изменения в клиенте: выбранные TCP-порты из разрешённого списка, таймаут простоя, состав TCP/UDP-последовательности, таймаут последовательности и привязка к IPv4. Интерфейс, секрет, ID, диапазон knock-портов и пределы политики задаются сервером.

Список секретов без раскрытия ключей:

```sh
sudo /usr/local/sbin/knock-control list
```

Повторно экспортировать существующий секрет:

```sh
sudo /usr/local/sbin/knock-control export PROFILE_ID --out /root/client.knock.json
```

Передайте каждому клиенту **его** JSON-файл по защищённому каналу. Файл содержит секрет; после копирования на клиент установите права:

```sh
chmod 600 alice.knock.json
```

Если один файл выдан нескольким людям, они используют один профиль и общие настройки. Для независимых настроек выдавайте разные секреты.

### Один профиль на двух клиентах

Одинаковый QR/JSON можно импортировать на двух устройствах. При **разных внешних IPv4** ON, OFF и таймаут простоя действуют независимо: сервер хранит отдельную запись и отдельный таймаут для каждой пары «профиль + IPv4». Например, ON с `198.51.100.10` и ON с `203.0.113.20` открывают доступ обоим; OFF первого адреса снимает только его разрешение, включая уже установленное соединение. Трафик первого клиента не продлевает разрешение второго. HTTPS-статус показывает доступ для IP, с которого пришёл запрос.

Настройки принадлежат секрету и общие для обоих устройств: порты, длительность простоя, параметры последовательности и ограничения. Изменение настроек с любого устройства применяется ко всему профилю и сбрасывает его текущие разрешения на всех IP — затем каждому клиенту нужно снова нажать ON. Отзыв секрета также действует на все его копии. Параллельное сохранение настроек защищено проверкой ревизии; устаревшее изменение отклоняется.

Два устройства за одним NAT с одинаковым внешним IPv4 разделяют одну запись разрешения: их ON/OFF и сетевую активность сервер не различает. Для независимых настроек и отзыва используйте отдельные секреты.

## 3. Активация сервера

Сначала передайте файлы клиентам. Затем на сервере:

```sh
sudo /usr/local/sbin/knock-control activate
sudo systemctl enable knock-control-firewall.service knock-control.service knock-control-api.service
```

`activate` запускает HTTPS API, устанавливает firewall и запускает knockd. Новые и уже существующие подключения к защищённым портам без выданного разрешения блокируются. Если защищаете административный SSH-порт, подготовьте клиент **до активации** либо используйте консоль/VPN/другой административный порт.

Сервер поддерживает до 128 выданных профилей. Разрешённые политиками порты входят в общий список защищённых портов, даже если конкретный клиент сейчас выбрал только часть из них. Отключение или отзыв последнего секрета не делает порты общедоступными.

API по умолчанию слушает HTTPS на TCP 8443. Он доступен независимо от кнопок Вкл/Выкл и требует подпись выданным секретом. Внешний firewall должен пропускать API и knock-пакеты до сетевого интерфейса сервера. Порт API нельзя включать в клиентские защищённые порты.

## 4. Телефон и расширение без помощника

После установки серверного пакета приложение доступно на `https://server.example.com:8443/app/`. При первом открытии импортируйте QR камерой, изображением из галереи или JSON. Обычная камера телефона также может открыть ссылку QR: профиль импортируется автоматически. Затем нажмите **ON** и откройте нужный SSH/RDP/веб-клиент. В дальнейшем профиль уже сохранён: откройте приложение → ON. Кнопка OFF отключает разрешение, настройки меняют порты и время простоя в пределах политики.

| Браузер | Установка |
|---|---|
| Firefox Android 142+ | Подписанный пакет `firefox-mobile` либо веб-приложение |
| Chrome Android | Веб-приложение: откройте QR-ссылку, выберите «Установить приложение» / «Добавить на главный экран» |
| Safari / Chrome / Firefox на iPhone/iPad | Веб-приложение; для ярлыка используйте Safari → «Поделиться» → «На экран Домой» |
| Chrome/Chromium/Edge на компьютере | Распаковать `knock-control-chromium-browser.zip`, загрузить папку через режим разработчика |
| Firefox на компьютере | Пакет `firefox-mobile` также работает без помощника |

Один XPI/ZIP нельзя установить как расширение во все браузеры телефона. Для Safari Web Extension нужна отдельная оболочка Apple/Xcode; в этой поставке iPhone обслуживает веб-приложение. Установка веб-приложения описана в [инструкции Apple](https://support.apple.com/en-lamr/guide/iphone/iphea86e5236/ios); разработка мобильных дополнений — в [инструкции Mozilla](https://extensionworkshop.com/documentation/develop/developing-extensions-for-firefox-for-android/).

Сборка пакетов:

```sh
python3 scripts/package-extension.py
```

Полный архив исходников с готовыми браузерными пакетами собирается командой `python3 scripts/package-release.py`: `dist/knock-control-3.0.0-source.zip`. Внутри папки `packages` находятся ZIP/XPI, рядом — исходники и установщики сервера. Контрольные суммы артефактов: `dist/SHA256SUMS`.

- `dist/knock-control-chromium-browser.zip` — HTTPS-расширение без помощника; папка `dist/chromium-browser` для «Загрузить распакованное расширение».
- `dist/knock-control-firefox-mobile.unsigned.xpi` — готовый архив **без подписи**. Обычный Firefox требует подпись Mozilla; переименование ZIP не создаёт подпись.
- `dist/knock-control-web-app.zip` — статические файлы веб-клиента; `install-server.sh` устанавливает их автоматически.
- `dist/knock-control-chromium.zip` и `dist/knock-control-firefox.unsigned.xpi` — настольный TCP/UDP-вариант с помощником, описанный ниже.

Для проверки дополнения на компьютере загрузите `dist/firefox-mobile/manifest.json` через `about:debugging`. Для постоянной установки, в том числе Android, владелец дополнения должен подписать его своим аккаунтом AMO. Подготовлен сценарий:

```sh
# Установите Node.js и web-ext. Задайте WEB_EXT_API_KEY и WEB_EXT_API_SECRET
# своим безопасным способом; не сохраняйте их в проекте.
./scripts/sign-firefox.sh firefox-mobile
```

Эта команда **отправляет исходники в Mozilla** для unlisted-подписи и сохраняет результат в `dist/signed-firefox-mobile`. Из этой среды отправка не выполнялась; подписанного XPI и публикации в магазине нет. Требование подписи описано в [правилах Mozilla](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/). Отладка Android возможна через `web-ext run -t firefox-android` и подключённый по ADB телефон по документации Mozilla.

При первом ON расширение запросит доступ только к домену выданного профиля. В веб-приложении разрешены только профили текущего сервера; для другого сервера откройте его QR-ссылку. IPv4 определяется по HTTPS-соединению автоматически. API подключается напрямую: прокси с подменой IP и заголовки `X-Forwarded-For` не поддерживаются. Не используйте разные исходящие IP для ON и защищённого сервиса.

В мобильном/HTTPS-режиме последовательность передаётся **внутри подписанного HTTPS-запроса** вместе с подтверждением HMAC-SHA256, а не физическими TCP/UDP-пакетами на knock-порты: WebExtensions и веб-страницы не имеют произвольных raw sockets. Сервер проверяет последовательность, время, источник и одноразовый nonce и применяет тот же профиль iptables/ipset. API открыт на отдельном порту и не продлевает таймаут сервиса. Настольный вариант ниже сохраняет настоящий port knocking через libpcap.

Профили HTTPS-расширения хранятся в локальном `storage.local`, веб-приложения — в `localStorage` данного сервера, без синхронизации с облаком. Это секреты в профиле браузера, отдельного пароля/шифрования хранилища нет. Очистка данных сайта или удаление расширения требует повторного импорта. Service Worker кеширует только открытые файлы интерфейса, не QR и не ответы API.

## 5. Настольное расширение с TCP/UDP и локальным помощником

На компьютере с браузером из каталога проекта:

```sh
python3 scripts/package-extension.py
```

**Chrome / Chromium / Edge:** откройте `chrome://extensions` (`edge://extensions` для Edge), включите режим разработчика, выберите «Загрузить распакованное расширение» → `dist/chromium`. Скопируйте ID и выполните **без sudo**:

```sh
python3 scripts/install-native.py --chrome-id ВАШ_ID
```

**Firefox:** откройте `about:debugging#/runtime/this-firefox`, загрузите временное дополнение из `dist/firefox/manifest.json`, затем выполните **без sudo**:

```sh
python3 scripts/install-native.py --firefox
```

Временное дополнение Firefox удаляется при перезапуске браузера. Для постоянной установки архив нужно подписать через Mozilla. Архивы `dist/knock-control-*.zip` не опубликованы в магазинах.

Оба параметра установщика можно совместить. Помощник устанавливается в `~/.local/lib/knock-control`. Расширению требуется только `nativeMessaging`; доступ к страницам и истории не запрашивается. Обмен соответствует [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) и [Firefox Native Messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging).

Откройте настройки расширения:

1. В разделе импорта выберите выданный сервером JSON-файл либо изображение QR.
2. Нажмите **Вкл**: при отсутствии сохранённого IPv4 помощник получит его с сервера автоматически. «Получить настройки с сервера» позволяет обновить данные отдельно; при другом маршруте knock-пакетов укажите внешний IPv4 вручную.
3. При необходимости нажмите «Показать ключ подключения» и добавьте ключ в Google Authenticator, тип «По времени».
4. В панели расширения выберите профиль и нажмите **Вкл**. После отправки проверьте доступ к сервису или нажмите «Проверить».
5. Нажмите **Выкл**, чтобы сразу снять разрешение. Таймаут ждать не требуется.

Можно импортировать несколько файлов и переключаться между ними. Получение/изменение настроек подписывается секретом активного профиля. У одного секрета нет доступа к списку или настройкам других секретов.

## Таймаут по неактивности

Для каждого секрета используется собственный ipset с разрешёнными IPv4. Вкл добавляет IP с `idle_timeout`. Входящий и исходящий TCP-трафик установленного соединения к разрешённым портам продлевает таймаут в ядре посредством `SET --exist --timeout`. Это поведение описано в [документации Netfilter](https://ipset.netfilter.org/iptables-extensions.man.html).

Например, при `idle_timeout=600` передача данных может идти часами. После последнего пакета защищённого соединения доступ отключится через 600 секунд. TCP keepalive и SSH keepalive тоже считаются сетевой активностью; это таймаут сетевого трафика, а не действий человека в приложении.

Knock-пакеты, неавторизованный шум, обновление статуса и изменения через API не считаются активностью защищённого сервиса. Простая проверка TCP-подключением к самому защищённому порту является активностью.

Выкл удаляет IP только из набора выбранного секрета. Если тот же IP имеет разрешение другого секрета на тот же порт, оно продолжает действовать: права складываются. При разных портах и разных секретах разрешения независимы.

Применение новых настроек сбрасывает текущие разрешения **только изменённого профиля**. Повторно нажмите Вкл. Остальные наборы сохраняются; knockd получает SIGHUP вместо остановки. При загрузке нового конфига незавершённые knock-последовательности сбрасываются, поэтому запрос, попавший ровно на обновление, может потребовать повтора.

## Отзыв и администрирование

Отозвать секрет на сервере:

```sh
sudo /usr/local/sbin/knock-control revoke PROFILE_ID
```

Это сразу убирает его разрешения, исключает последовательности из конфига и отклоняет запросы к API. Другие профили сохраняются. Вернуть отозванный ключ через клиент нельзя; выдайте новый командой `issue`.

Глобальное управление службами остаётся у администратора:

```sh
sudo systemctl status knock-control.service knock-control-api.service
sudo journalctl -u knock-control.service -u knock-control-api.service -n 100
sudo /usr/local/sbin/knockd --check -c /etc/knock-control/knockd.conf
sudo iptables -S KNOCK_CONTROL
sudo iptables -S KNOCK_CONTROL_ACTIVITY
sudo ipset list
```

Данные: `/etc/knock-control/settings.json`, конфиг демона `/etc/knock-control/knockd.conf`, TLS-ключ и сертификат в том же каталоге. Клиентские профили: `~/.config/knock-control/profiles.json`, права 0600. Копии выданных JSON-файлов тоже содержат секреты. В настольном режиме с помощником браузер не хранит секреты в extension storage. Хранилища HTTPS-режима описаны выше.

Если ранее была установлена версия с одним клиентским секретом и управлением по SSH, сначала остановите старый knockd, сохраните резервные копии `settings.json` и `knockd.conf`, перенесите старые файлы из этих двух путей, затем выполните новую инициализацию и выдачу. Старые клиентские JSON не импортируются в v2: секреты нужно создать на сервере заново. Старое правило `/etc/sudoers.d/knock-control` для клиентов больше не требуется.

## Протокол и защита

TOTP соответствует [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238): Base32, SHA1, 6 цифр, 30 секунд. Используются текущее и соседние окна ±30 секунд. Внутри стандарта Google Authenticator остаётся HMAC-SHA1. Код можно ввести вручную в настольном клиенте или вычислить автоматически в клиенте. Для обычного сценария ON ввод кода не нужен.

Имя двери включает ID профиля: `PROFILE_ID.open` / `PROFILE_ID.close`. Из кода, действия и IPv4 получается последовательность:

```text
SHA256(ASCII("knock-control:v1:" + door + ":" + source + ":" + code))
port[i] = base + digest[i]
source = внешний IPv4, либо "-" при отключённой привязке
```

Следует подписанное UDP-подтверждение на `base`, 60 байт:

```text
"KNC1" (4) | TOTP counter, uint64 big-endian (8) | random nonce (16) | HMAC-SHA256 (32)
HMAC key = Base32Decode(secret)
message = ASCII("knock-control:confirm:v1:") + counter + nonce + ASCII(door + ":" + source)
```

Подтверждение требуется и для Вкл, и для Выкл. Одна последовательность, случайно собранная из плотного шума, не выполняет команду. Попытки имеют фиксированный таймаут; посторонние пакеты не продлевают его. Ограничение памяти: 4096 попыток в целом, 8 на IP/дверь, 1024 использованные подписи. Переполнение не разрешает доступ. Кэш повторов knock-подтверждений находится в памяти: полный перезапуск процесса сбрасывает его. Ранее перехваченный обмен потенциально можно повторить с того же IP в ещё допустимом временном окне после перезапуска.

Управление настройками и браузерными ON/OFF: HTTPS `POST /v1/control`, подпись HMAC-SHA256 по ID/времени/nonce/телу. Авторизованный ID берётся из проверенного заголовка; тело не может подставить другой ID. Окно времени ±60 секунд, nonce API хранятся в SQLite и не теряются при перезапуске API. Настольный помощник сверяет SHA256 сертификата из выданного файла **до отправки авторизованного запроса**. При инициализации сервер выдаёт самоподписанный сертификат; для помощника доверие устанавливается защищённой передачей клиентского файла. В браузерном режиме нужен сертификат, доверенный браузером.

TLS-соединения ограничены 32 параллельными обработчиками с таймаутами, тело запроса — 64 КиБ, запросы ограничены по источнику. Это защита ресурсов и работа при обычном шуме, а не гарантия доступности при DDoS или потере пакетов. Расширение сообщает об отправке knocks; подтверждение фактического состояния получает отдельным запросом статуса для IP, наблюдаемого API.

Секрет находится у клиента для подписей и автоматического TOTP. Ручной код Google Authenticator не образует отдельный второй фактор при компрометации клиентского компьютера.

## Границы firewall

Цепочка `KNOCK_CONTROL` подключается первой в INPUT; `KNOCK_CONTROL_ACTIVITY` — первой в OUTPUT для учёта исходящей активности. Используются отдельные наборы `kc_PROFILE_ID`. Сначала разрешаются права всех активных профилей, затем блокируются общие защищённые порты. Другие таблицы и цепочки не очищаются.

Эта версия управляет IPv4/TCP к сервисам самого хоста. IPv6 и контейнерный FORWARD не защищаются автоматически. Cloud security groups должны пропускать HTTPS API и knock-диапазоны; смотреть диапазон профиля можно в выданном файле. UDP-подтверждение должно доходить до интерфейса сервера, хотя слушающего UDP-сокета нет — используется libpcap. Конкурирующие UFW/firewalld/другие менеджеры могут изменить порядок правил: интеграцию нужно согласовать отдельно.

Старые `sequence =` и `otp =` доступны при ручном запуске knockd, но новый контроллер генерирует только `totp =`. Исходный `/etc/knockd.conf` не перезаписывается. Старый `otp =` не получает подписанное подтверждение и сохраняет строгую последовательность.

## Проверки

```sh
./scripts/test.sh
sudo unshare --net python3 tests/integration_netns.py
sudo unshare --net python3 tests/integration_shared_profile_netns.py
```

Первая команда собирает C с AddressSanitizer/UndefinedBehaviorSanitizer, проверяет RFC-векторы, повреждённые пакеты, шум и предел 4096 попыток; запускает Python-тесты авторизации, политик и настоящего TLS, проверяет JS и собирает расширения.

Последний запуск: 20 Python-тестов пройдены, в том числе QR, подписи браузерного транспорта и смена TLS с проверкой пары ключей/сертификата и откатом при ошибке перезапуска. Обе сборки Firefox проходят `web-ext lint --warnings-as-errors` без ошибок и предупреждений.

Вторая использует реальные libpcap, TCP/UDP, iptables/ipset и HTTPS API в изолированном network namespace. Проверяются независимые профили, активный трафик дольше idle-таймаута, истечение при простое на фоне шума/API-запросов, ручное отключение установленного соединения, сохранение другого профиля, неверная подпись/повтор/чужой ID, изменение настроек через API, горячая загрузка, отзыв всех ключей и выдача нового после пустого конфига. Основные сетевые правила машины не изменяются.

Последний сценарий, включая браузерный HTTPS ON/OFF, прошёл на **273 065 шумовых пакетах за 30,71 секунды**. Это функциональная проверка данной нагрузки, не измерение предельной производительности. При выдаче нового диапазона после пустого конфига сценарий ожидает асинхронное применение SIGHUP перед первой последовательностью.

Третья команда отдельно проверяет **одинаковый выданный профиль на двух разных IPv4**, `127.0.0.2` и `127.0.0.3`, с реальными сокетами, libpcap, TLS и iptables/ipset внутри изолированного namespace. Для TCP/UDP и HTTPS проверяются одновременный ON, OFF в обе стороны, блокировка своего установленного соединения с сохранением чужого, раздельное истечение простоя, продление только активного IP и статус для адреса запроса. Также проверяются общие настройки и отклонение устаревшей ревизии. Прогон прошёл на **351 600 шумовых пакетах за 39,36 секунды**; трафик сервиса одного IP не удержал разрешение второго. Это локальная сетевая проверка с разными адресами источника, а не испытание двух физических устройств через разных интернет-провайдеров.

Проверки настоящего расширения и Native Messaging в обоих браузерах:
