# Knock Control 3

Готовые расширения, веб-приложение и OpenWrt APK: [релиз v3.0.0-r6](https://github.com/rdmitry0911/knock/releases/tag/v3.0.0-r6). Для OpenWrt выберите пакет своей архитектуры. **Firefox XPI пока не подписаны Mozilla и не устанавливаются постоянно в обычный Firefox.** Chrome/Edge устанавливаются распаковкой ZIP через режим разработчика. [Установка, получение подписи и ограничения](doc/BROWSER_INSTALLATION_RU.md).

Knock Control предоставляет управляемый аварийный доступ к чувствительным сервисам, которые в штатном режиме закрыты от публичного интернета. Сервер создаёт секреты и выдаёт клиентам QR и JSON-профили. Каждый секрет имеет собственные настройки и ограничения; один профиль можно использовать на нескольких устройствах с разными внешними IPv4. Порядок работы: **импорт один раз → ON → работа с сервисом**. OFF сразу снимает разрешение своего IP. Есть расширения Chrome/Firefox и веб-приложение для мобильных браузеров.

- **Вкл** — отправить TOTP-последовательность и подписанное подтверждение, разрешить выбранные правила TCP/UDP/ICMP для своего IPv4.
- **Выкл** — немедленно снять разрешение своего профиля/IP. Защищённый трафик, включая установленное соединение, перестаёт пропускаться, если его не разрешает другой профиль.
- **Автоматическое отключение** — после заданного времени **без трафика к защищённому сервису**. Активное соединение продлевает разрешение; шум в knock-диапазоне и обращения к API не продлевают его.
- **Настройки** — изменить только профиль своего секрета и только в пределах политики, выданной администратором.

Служба knockd продолжает работать и принимать новые запросы, когда все клиенты нажали «Выкл». Клиентские кнопки не останавливают общую службу. Несколько разных секретов могут работать одновременно.

## Мотивация: аварийный доступ при недоступном VPN

Механизм может служить заранее подготовленным администратором **аварийным входом («бэкдором»)** в трудных случаях, когда основной способ доступа, например VPN, не работает: из-за сбоя VPN-службы, проблем маршрутизации, настроек клиента или недоступности VPN-протокола в текущей сети. Через этот независимый от VPN канал можно временно получить доступ к SSH, RDP, интерфейсам администрирования и другим чувствительным TCP/UDP-сервисам, которые в обычном режиме недоступны из публичного интернета, восстановить основной доступ и затем закрыть аварийный вход кнопкой OFF.

Авторизованный клиент подтверждает владение выданным сервером секретом с помощью TOTP-последовательности и подписанного подтверждения. Сервер разрешает выбранные порты только для IPv4 этого клиента. Пока клиент работает с сервисом, разрешение продлевается; после простоя оно автоматически истекает. Остальные адреса продолжают блокироваться. Доступ к самому сервису проходит его обычную аутентификацию.

Для аварийного использования установите и настройте механизм заранее, сохраните профиль на клиенте и проверьте доступ из внешней сети. Сервер и выбранный транспорт управления должны оставаться достижимыми: TCP/UDP-knocks для настольного режима, UDP ICE-knock из браузера либо HTTPS API. Тогда для открытия порта не требуется работающий VPN или уже открытый SSH-сеанс. Полная недоступность сервера или блокировка всех необходимых сетевых путей делает этот канал недоступным тоже.

Для настольного ON/OFF без доступного API клиенту нужен актуальный внешний IPv4: заранее сохранённый или введённый вручную в настройках. Обычно помощник определяет его через API автоматически. После смены внешнего адреса сохранённый IP нужно обновить.

Поддерживаются TCP/UDP-сервисы самого хоста, диапазоны портов, ICMP, маршрутизируемый доступ к внутреннему хосту и DNAT-проброс на его IPv4/порт. Правила создаются на сервере, затем связываются с профилями. Сервис на другом хосте должен иметь обратный маршрут через этот сервер/роутер. Для сервиса, слушающего только `localhost`, потребуется прокси.

## Именованные правила и привязка к профилю

Администратор задаёт правила на сервере. Профиль содержит два списка: `rules` — выбранные правила, `allowed_rules` — правила, которые этот секрет вправе выбирать в расширении. ON разрешает выбранные правила только для IP клиента; OFF снимает это разрешение. Два IP с одним профилем независимы. Клиент не может изменить внутренний адрес, тип правила или расширить разрешённый список.

| Тип | Назначение |
| --- | --- |
| `input` | Сервис самого сервера/роутера: TCP, UDP или ICMP |
| `forward` | Маршрутизируемый доступ к `dest_ip`, без изменения адреса назначения |
| `dnat` | Проброс внешнего TCP/UDP-порта на `dest_ip`, при необходимости на другой `dest_port` |

`ports` — список отдельных портов и включительных диапазонов, например `22,443,10000-10100`. Каждое правило имеет один протокол `tcp`, `udp` или `icmp`; для TCP и UDP одного сервиса создайте два правила. Диапазон DNAT сохраняет номера портов; `dest_port` разрешён только для одного внешнего порта. ICMP по умолчанию открывает только echo-request (ping); `icmp_type=any` открывает все типы ICMP. Правила применяются на указанном `interface`; по умолчанию это интерфейс сервера. Указывайте физическое имя WAN, например `wan`, а не имя зоны firewall.

Одинаковые команды работают в OpenWrt и обычном Linux после `init`:

```sh
# 2222/TCP на внешнем адресе → 192.168.1.10:22
knock-control rule-set ssh_lan --type dnat --protocol tcp --ports 2222 \
  --dest-ip 192.168.1.10 --dest-port 22
# Проброс UDP на внутренний сервис:
knock-control rule-set udp_lan --type dnat --protocol udp --ports 5555 \
  --dest-ip 192.168.1.20 --dest-port 5556
# TCP-диапазон на самом сервере, UDP-диапазон на самом сервере, ping:
knock-control rule-set tcp_range --type input --protocol tcp --ports 10000-10100
knock-control rule-set udp_range --type input --protocol udp --ports 11000-11100
knock-control rule-set ping --type input --protocol icmp
knock-control rules
# Выдать секрет с готовым набором правил; --ports для него не требуется:
knock-control issue --name Phone --rules ssh_lan,udp_lan,ping \
  --allowed-rules ssh_lan,udp_lan,ping,tcp_range,udp_range \
  --idle-timeout 600 --out /root/phone.json --qr-out /root/phone.png
```

Если сервер ещё не активирован, передайте QR клиенту и выполните `knock-control activate`. Если активирован — новый профиль уже доступен. В расширении обновите статус: будут показаны разрешённые имена и назначения правил. Поле «Правила профиля» выбирает список; поле дополнительных TCP-портов можно оставить пустым. Сохранение списка сбрасывает разрешения этого профиля, после чего нужен ON. Прежние профили с `--ports` продолжают работать.

В OpenWrt те же правила задаются обычными секциями **`/etc/config/knock-control`**:

```uci
config rule 'ssh_lan'
        option type 'dnat'
        option protocol 'tcp'
        option interface 'wan'
        list ports '2222'
        option dest_ip '192.168.1.10'
        option dest_port '22'

config rule 'udp_range'
        option type 'input'
        option protocol 'udp'
        list ports '11000-11100'

config rule 'ping'
        option type 'input'
        option protocol 'icmp'
        option icmp_type 'echo-request'
```

Чтобы связать правила с **уже выданным** профилем, возьмите его ID из `knock-control list`. Секрет и остальные параметры профиля сохраняются. Например, замените `PROFILE_ID` реальным ID:

```sh
profile_id='PROFILE_ID'
uci set "knock-control.$profile_id.named_rules=1"
uci -q delete "knock-control.$profile_id.rules"
uci -q delete "knock-control.$profile_id.allowed_rules"
uci add_list "knock-control.$profile_id.rules=ssh_lan"
uci add_list "knock-control.$profile_id.rules=ping"
uci add_list "knock-control.$profile_id.allowed_rules=ssh_lan"
uci add_list "knock-control.$profile_id.allowed_rules=ping"
uci add_list "knock-control.$profile_id.allowed_rules=udp_range"
# Только если дополнительные старые TCP-порты больше не нужны:
uci -q delete "knock-control.$profile_id.ports"
uci -q delete "knock-control.$profile_id.allowed_ports"
uci commit knock-control
/etc/init.d/knock-control reload
```

`named_rules=1` сохраняет явный пустой список при отключении всех правил в профиле. Ручной reload увеличивает ревизии и сбрасывает текущие разрешения; в клиентах обновите статус и нажмите ON. В обычном Linux эквивалентные определения хранятся в объекте `rules` файла `/etc/knock-control/settings.json`; для создания правил и выдачи профилей предпочтительны команды выше.

Для FORWARD/DNAT на обычном Linux нужен `net.ipv4.ip_forward=1`, маршруты до внутреннего хоста и обратный маршрут через этот сервер. В OpenWrt маршрутизация обычно уже включена. SNAT/masquerade эта версия не добавляет; внутренний хост видит реальный адрес клиента. Не дублируйте один внешний порт существующим безусловным пробросом firewall. Противоречащие друг другу именованные DNAT-назначения на одном интерфейсе/протоколе/порту отклоняются.

Определения правил задают защищённые сервисы: после активации они закрыты без разрешения, даже если профиль отозван или правило не выбрано. Удаление определения администратором снимает эту защиту и возвращает обработку штатному firewall. Изменение определения через `rule-set` сбрасывает разрешения профилей; выбор разрешённого списка в расширении затрагивает только его профиль. Переадресованные соединения проверяются в обоих направлениях, поэтому сохранённый conntrack/NAT не обходит OFF и таймаут.

## Требования

Сервер: обычный Linux с systemd, libpcap, OpenSSL, iptables и ipset/ядро с модулем SET **либо OpenWrt 25.12 с procd и firewall4/nftables**, описанный ниже. Мобильный клиент: современный браузер с HTTPS/Web Crypto; для расширения Firefox Android — 142+. Клиент HTTPS работает без Python и локального помощника. Настольный режим с настоящими TCP/UDP-knocks требует Linux, Python 3 и обычную установку Chrome/Chromium/Edge или Firefox 142+; Snap/Flatpak требуют отдельной настройки Native Messaging. IPv6 и облачные firewall требуют отдельной интеграции; правила FORWARD/DNAT работают с IPv4 при настроенной маршрутизации.

## 1. Установка на сервере

Скопируйте проект на сервер и из его каталога выполните:

```sh
sudo apt-get install build-essential libpcap-dev libssl-dev openssl python3 iptables ipset
./scripts/build.sh
sudo ./scripts/install-server.sh
```

Первичная настройка выполняется администратором на сервере. SSH может использоваться администратором для установки и выдачи файлов, но клиентам SSH-аккаунт и sudo не нужны.

Инициализируйте сервер, заменив адрес и интерфейс:

```sh
sudo /usr/local/sbin/knock-control init \
  --public-host server.example.com \
  --interface ens3 \
  --api-port 8443
```

Команда создаёт базу, TLS-ключ и сертификат. Она отказывается перезаписывать существующую базу. Адресом может быть публичный IPv4 или домен. Посмотреть интерфейсы можно через `ip -br -4 addr`. При необходимости API можно слушать на конкретном IPv4 через `--bind`; адрес в `--public-host` должен вести на доступный клиенту слушающий интерфейс.

Для телефонов и расширений без помощника установите **сертификат HTTPS, которому доверяет браузер**, на имя из `--public-host`. Например, после получения сертификата у вашего CA:

```sh
sudo knock-control tls \
  --cert /etc/letsencrypt/live/server.example.com/fullchain.pem \
  --key /etc/letsencrypt/live/server.example.com/privkey.pem
```

Сертификат нужно получить отдельно; команда проверяет пару и устанавливает её в API. Сервер должен быть доступен по IPv4. После продления сертификата повторите `tls`; у настольных клиентов с закреплённым отпечатком потребуется повторный экспорт/импорт профиля. Для браузерного клиента действует обычное доверие CA и имя узла, а не pin из JSON. Самоподписанный сертификат из `init` подходит для настольного помощника; мобильный импорт/камера и веб-приложение требуют доверенного HTTPS. Отключать проверку сертификата в рабочем браузере не нужно.

Инициализация и выдача первых файлов **до активации** не включают защиту портов. Это позволяет сначала передать файлы клиентам, а затем включить правила без потери возможности настроить клиент.

## 2. Выдача отдельных секретов

Например, выдать Alice доступ к порту 443 с возможностью выбирать 443/8444 и менять простой до часа:

```sh
sudo /usr/local/sbin/knock-control issue \
  --name Alice \
  --ports 443 \
  --allowed-ports 443,8444 \
  --idle-timeout 600 \
  --max-idle-timeout 3600 \
  --out /root/alice.knock.json \
  --qr-out /root/alice.knock.png
```

Выдать Bob другой секрет и другие настройки:

```sh
sudo /usr/local/sbin/knock-control issue \
  --name Bob \
  --ports 2222 \
  --idle-timeout 120 \
  --max-idle-timeout 600 \
  --out /root/bob.knock.json
```

QR можно создать повторно для уже выданного профиля:

```sh
sudo knock-control qr PROFILE_ID --out /root/client.png
sudo knock-control qr PROFILE_ID --out /root/client.svg
sudo knock-control qr PROFILE_ID --terminal
```

Генерация и распознавание QR выполняются локально, без внешних QR-сервисов. PNG/SVG/JSON создаются с правами 0600. QR содержит полный профиль, включая секрет: передавайте его только адресату. Ссылка имеет вид `https://server:8443/app/#import=kc2_…`; секрет находится во фрагменте, который браузер не отправляет HTTP-серверу. Приложение сразу удаляет фрагмент из адреса и истории. Не публикуйте этот QR. QR `otpauth://` от Google Authenticator не заменяет полный профиль подключения.

Без `--allowed-ports` разрешённый список совпадает с `--ports`. `--native-only` запрещает браузерный ON/OFF для данного секрета: остаётся настоящий TCP/UDP-клиент. По умолчанию разрешены оба транспорта. Флаг `--fixed-settings` запрещает клиенту менять настройки, сохраняя кнопки Вкл/Выкл. Каждый вызов `issue` генерирует на сервере новый случайный Base32-секрет 160 бит, ID и отдельный диапазон knock-портов. Клиент не задаёт секрет при выдаче и не может создавать новые профили через API.

Доступные изменения в клиенте: выбранные имена правил и дополнительные TCP-порты из разрешённых списков, таймаут простоя, состав TCP/UDP-последовательности, таймаут последовательности и привязка к IPv4. Интерфейс, секрет, ID, диапазон knock-портов и пределы политики задаются сервером.

Список секретов без раскрытия ключей:

```sh
sudo /usr/local/sbin/knock-control list
```

Повторно экспортировать существующий секрет:

```sh
sudo /usr/local/sbin/knock-control export PROFILE_ID --out /root/client.knock.json
```

Передайте каждому клиенту **его** JSON-файл по защищённому каналу. Файл содержит секрет; после копирования на клиент установите права:

```sh
chmod 600 alice.knock.json
```

Если один файл выдан нескольким людям, они используют один профиль и общие настройки. Для независимых настроек выдавайте разные секреты.

### Один профиль на двух клиентах

Одинаковый QR/JSON можно импортировать на двух устройствах. При **разных внешних IPv4** ON, OFF и таймаут простоя действуют независимо: сервер хранит отдельную запись и отдельный таймаут для каждой пары «профиль + IPv4». Например, ON с `198.51.100.10` и ON с `203.0.113.20` открывают доступ обоим; OFF первого адреса снимает только его разрешение, включая уже установленное соединение. Трафик первого клиента не продлевает разрешение второго. HTTPS-статус показывает доступ для IP, с которого пришёл запрос.

Настройки принадлежат секрету и общие для обоих устройств: порты, длительность простоя, параметры последовательности и ограничения. Изменение настроек с любого устройства применяется ко всему профилю и сбрасывает его текущие разрешения на всех IP — затем каждому клиенту нужно снова нажать ON. Отзыв секрета также действует на все его копии. Параллельное сохранение настроек защищено проверкой ревизии; устаревшее изменение отклоняется.

Два устройства за одним NAT с одинаковым внешним IPv4 разделяют одну запись разрешения: их ON/OFF и сетевую активность сервер не различает. Для независимых настроек и отзыва используйте отдельные секреты.

## 3. Активация сервера

Сначала передайте файлы клиентам. Затем на сервере:

```sh
sudo /usr/local/sbin/knock-control activate
sudo systemctl enable knock-control-firewall.service knock-control.service knock-control-api.service
```

`activate` запускает HTTPS API, устанавливает firewall и запускает knockd. Новые и уже существующие подключения к защищённым портам без выданного разрешения блокируются. Если защищаете административный SSH-порт, подготовьте клиент **до активации** либо используйте консоль/VPN/другой административный порт.

Сервер поддерживает до 128 выданных профилей, 128 именованных правил и 64 имени правила в списке одного профиля. Разрешённые политиками порты входят в общий список защищённых портов, даже если конкретный клиент сейчас выбрал только часть из них. Отключение или отзыв последнего секрета не делает порты общедоступными.

API по умолчанию слушает HTTPS на TCP 8443. Он доступен независимо от кнопок Вкл/Выкл и требует подпись выданным секретом. Внешний firewall должен пропускать API и knock-пакеты до сетевого интерфейса сервера. Порт API нельзя включать в клиентские защищённые порты.

## 4. Телефон и расширение без помощника

### ON/OFF через WebRTC без открытого порта управления

Сервер r6 и новые QR/JSON-профили поддерживают `ice_version: 1`. После импорта браузерный клиент по умолчанию отправляет ON/OFF через WebRTC ICE: браузер посылает UDP STUN Binding Request на базовый knock-порт профиля, а daemon перехватывает пакет через libpcap до firewall. **Слушающий UDP-сокет, STUN-сервер на knock-хосте и доступный HTTPS API для ON/OFF не нужны.** Это отдельный транспорт подписанной команды; обычная последовательность TCP/UDP для настольного помощника сохраняется.

Порядок: обновить сервер → `knock-control export ID --out /root/phone.json --qr-out /root/phone.png` → импортировать новый профиль → ON. В «Способе подключения» можно явно выбрать ICE или прежний HTTPS. Старые профили без признака ICE продолжают использовать HTTPS до повторного экспорта/импорта. Если `knock_host` содержит DNS-имя, укажите числовой IPv4 в локальном поле «IPv4 knock-сервера».

При привязке к IP клиент определяет внешний IPv4 через `stun:stun.cloudflare.com:3478`; можно задать свой STUN. Этот провайдер видит исходный IP, но не получает секрет или подписанную команду. Если указать «Мой внешний IPv4» вручную, внешнего STUN-запроса нет. При смене сети ручной адрес нужно обновить. Исходящий адрес UDP-knock и защищённого сервиса должен совпадать: разные маршруты VPN/прокси, несколько WAN и некоторые NAT могут требовать отдельной настройки. Если UDP/WebRTC заблокированы, доступен явный выбор HTTPS; скрытого переключения транспорта нет.

Подпись HMAC-SHA256 связывает ID, ON/OFF, ревизию, временной счётчик, время команды, случайный nonce и IPv4. Секрет остаётся на клиенте. SQLite хранит использованные nonce и порядок команд отдельно для каждого IPv4: повтор пакета после перезапуска не открывает доступ, запоздалый ON не отменяет более новый OFF. Часы клиента и сервера должны быть синхронизированы; старые ревизии отклоняются.

ICE работает без ответа сервера. Сообщение «отправлен» означает отправку попытки, а не подтверждённое открытие firewall. Проверить результат можно подключением к защищённому сервису; кнопка «Проверить» и изменение настроек используют HTTPS API. API можно держать доступным только через административный маршрут/VPN: в OpenWrt задайте `uci set knock-control.main.api_bind='127.0.0.1'`, затем `uci commit knock-control` и `/etc/init.d/knock-control reload`. Установленное расширение содержит файлы клиента локально; веб-приложение нужно предварительно загрузить и сохранить для работы без доступного сайта. Первоначальное открытие QR-ссылки требует доступного HTTPS-сайта.


После установки серверного пакета приложение доступно на `https://server.example.com:8443/app/`. При первом открытии импортируйте QR камерой, изображением из галереи или JSON. Обычная камера телефона также может открыть ссылку QR: профиль импортируется автоматически. Затем нажмите **ON** и откройте нужный SSH/RDP/веб-клиент. В дальнейшем профиль уже сохранён: откройте приложение → ON. Кнопка OFF отключает разрешение, настройки меняют порты и время простоя в пределах политики.

# Установите Node.js и web-ext. Задайте WEB_EXT_API_KEY и WEB_EXT_API_SECRET

Есть и [ручная загрузка в AMO без API-ключей](doc/BROWSER_INSTALLATION_RU.md). При обращении к HTTPS API расширение запросит доступ только к домену выданного профиля; ICE ON/OFF этого разрешения не требует. В веб-приложении разрешены только профили текущего сервера; для другого сервера откройте его QR-ссылку. В HTTPS-режиме IPv4 определяется по HTTPS-соединению автоматически. API подключается напрямую: прокси с подменой IP и заголовки `X-Forwarded-For` не поддерживаются. Не используйте разные исходящие IP для ON и защищённого сервиса.

В мобильном/HTTPS-режиме последовательность передаётся **внутри подписанного HTTPS-запроса** вместе с подтверждением HMAC-SHA256, а не физическими TCP/UDP-пакетами на knock-порты: WebExtensions и веб-страницы не имеют произвольных raw sockets. Сервер проверяет последовательность, время, источник и одноразовый nonce и применяет тот же профиль iptables/ipset. API открыт на отдельном порту и не продлевает таймаут сервиса. Настольный вариант ниже сохраняет настоящий port knocking через libpcap.

Профили HTTPS-расширения хранятся в локальном `storage.local`, веб-приложения — в `localStorage` данного сервера, без синхронизации с облаком. Это секреты в профиле браузера, отдельного пароля/шифрования хранилища нет. Очистка данных сайта или удаление расширения требует повторного импорта. Service Worker кеширует только открытые файлы интерфейса, не QR и не ответы API.

Оба параметра установщика можно совместить. Помощник устанавливается в `~/.local/lib/knock-control`. Расширению требуется только `nativeMessaging`; доступ к страницам и истории не запрашивается. Обмен соответствует [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) и [Firefox Native Messaging](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_messaging).

Откройте настройки расширения:

1. В разделе импорта выберите выданный сервером JSON-файл либо изображение QR.
2. Нажмите **Вкл**: при отсутствии сохранённого IPv4 помощник получит его с сервера автоматически. «Получить настройки с сервера» позволяет обновить данные отдельно; при другом маршруте knock-пакетов укажите внешний IPv4 вручную.
3. При необходимости нажмите «Показать ключ подключения» и добавьте ключ в Google Authenticator, тип «По времени».
4. В панели расширения выберите профиль и нажмите **Вкл**. После отправки проверьте доступ к сервису или нажмите «Проверить».
5. Нажмите **Выкл**, чтобы сразу снять разрешение. Таймаут ждать не требуется.

Можно импортировать несколько файлов и переключаться между ними. Получение/изменение настроек подписывается секретом активного профиля. У одного секрета нет доступа к списку или настройкам других секретов.

## OpenWrt 25.12: пакет и установка

Пакет `dist/openwrt/knock-control-3.0.0-r6.apk` собран официальным SDK OpenWrt **25.12.5 для x86_64** и проверен в QEMU. Ветка 25.12 использует APK; этот файл не предназначен для `opkg`/IPK из старых веток. Для ARM/MIPS и других архитектур нужен отдельный пакет, собранный соответствующим SDK.

Для **Gemtek W1700K, target `airoha/an7581`, ARM64** собрана отдельная версия: `dist/openwrt/airoha-an7581/knock-control-3.0.0-r6.apk`. Она установлена и проверена на физическом устройстве с OpenWrt SNAPSHOT `r35909-cee584714b`, ядром `6.18.44`: нативный контроллер C, libpcap/TOTP, генерация и декодирование QR, HTTPS API/uhttpd и SQLite. Проверки используют временные тестовые профили и loopback, не активируют защиту реальных сервисов; после установки нужна обычная первичная настройка.

В **r2 Python полностью исключён из OpenWrt-пакета и его зависимостей**. Контроллер `/usr/sbin/knock-control` написан на C; HTTPS обслуживает отдельный экземпляр штатного uhttpd, который не меняет настройки LuCI. PNG/SVG/терминальный QR создаются локально через libqrencode, PNG сжимается zlib. SQLite сохранён для совместимости постоянного журнала защиты от повторов. При проверке r2 на ARM64-роутере бинарный контроллер занимал 58 386 байт; замена r1 на r2 освободила около **7,8 МиБ flash** с учётом сжатия файловой системы. Python-интерпретатор и модули прежнего пакета удалились как ненужные зависимости. Размер установки на другом устройстве зависит от уже имеющихся библиотек.

Скопируйте APK на OpenWrt и установите от root:

```sh
apk update
apk add --allow-untrusted /tmp/knock-control-3.0.0-r6.apk
```

`--allow-untrusted` нужен для локального APK, не подписанного ключами официальных репозиториев OpenWrt. Проверку HTTPS этот параметр не отключает. Контрольная сумма пакета находится в `dist/openwrt/SHA256SUMS` или в каталоге соответствующей архитектуры. Зависимости устанавливаются через APK: libpcap, OpenSSL, json-c, SQLite, libqrencode, libuci, zlib, uhttpd с TLS, firewall4 и nftables с JSON. Готовый APK использует штатный backend `libustream-mbedtls`; при сборке собственного образа учитывайте выбранный TLS backend uhttpd. Размер APK не равен размеру установки с зависимостями.

Начиная с **r3**, основной конфиг OpenWrt — **`/etc/config/knock-control` в формате UCI**. Секция `server 'main'` содержит общие параметры, отдельная секция `profile 'ID'` — секрет, настройки и ограничения каждого профиля. Файл имеет права **0600**, поскольку содержит секреты. Установка, обновление, переустановка и резервное копирование sysupgrade сохраняют его.

При обновлении с r1/r2 прежний `/etc/knock-control/settings.json` автоматически переносится в UCI при запуске служб или контроллера. Копия исходного JSON сохраняется как `/etc/knock-control/settings.json.pre-uci`. Секреты, идентификаторы, ревизии, сертификаты и `api-replays.sqlite3` сохраняются; повторно импортировать клиентские профили не требуется. Если UCI уже инициализирован, старый JSON его не перезаписывает. Не удаляйте `/etc/knock-control`: там остаются сертификаты, постоянные данные и резервная копия миграции. При обновлении с r1 APK также удаляет ненужные зависимости Python, сохраняя зависимости других приложений.

Справка доступна без изменения конфигурации:

```sh
knock-control help
knock-control help init
knock-control init --help
```

`init` требует `--public-host`: внешний DNS-адрес или IPv4, по которому клиенты будут обращаться к роутеру. Без этого параметра контроллер выводит сообщение с примером команды и не создаёт конфигурацию или ключи. Имя интерфейса нужно брать из `ubus call network.interface.wan status`, поле `l3_device`.

Первичная настройка на OpenWrt, где `server.example.com` нужно заменить внешним адресом роутера, а `eth1` — именем реального WAN-устройства:

```sh
knock-control init --public-host server.example.com --interface eth1 --api-port 8443
# Для браузерного режима сначала установите доверенный сертификат:
knock-control tls --cert /путь/fullchain.pem --key /путь/privkey.pem
knock-control issue --name Phone --ports 2222 --idle-timeout 600 \
  --out /root/phone.json --qr-out /root/phone.png
# Передайте профиль клиенту, затем включите защиту:
knock-control activate
/etc/init.d/knock-control-firewall enable
/etc/init.d/knock-control-api enable
/etc/init.d/knock-control enable
```

Узнать WAN-устройство можно через `ubus call network.interface.wan status` и `ip -4 addr`. При выборе защищаемых портов сохраняются ограничения из основной инструкции; в частности, порт API нельзя включать в профиль. С r5 доступны именованные правила INPUT, FORWARD и DNAT для TCP/UDP, диапазонов портов и ICMP. IPv6 пока не поддерживается. Примеры привязки правил к профилю приведены в разделе «Именованные правила».

OpenWrt-версия использует **native nftables внутри `inet fw4`**, без добавления legacy iptables/ipset. Разрешения хранятся в отдельных наборах `kc_PROFILE_ID`; каждый IPv4 имеет собственный таймаут. Правила входа помещаются перед штатными разрешениями loopback и established-трафика, поэтому OFF останавливает уже установленное соединение. Разрешённый профилю IP получает доступ к выбранному сервису и через WAN; IPv4-порт API доступен для подписанных запросов независимо от ON/OFF. Проверки FORWARD также стоят перед established и flow-offload правилами fw4. Остальные цепочки fw4 не очищаются.

При изменении профиля атомарно обновляются только цепочки Knock Control и сбрасываются разрешения изменённого секрета; разрешения остальных профилей сохраняются. Обычный `firewall reload` в проверенной 25.12.5 сохраняет живые записи наборов. При наличии FORWARD/DNAT и активного `ft` применение правил выполняет reload fw4, чтобы сбросить потоки, ускоренные до введения защиты; защищённые потоки обходят добавление в flowtable. Сторонние ускорители и менеджеры firewall требуют отдельной проверки порядка обработки. После полной перезагрузки роутера старые разрешения исчезают: сохранённый профиль остаётся у клиента, нужно снова нажать ON.

Настройки и секреты профилей находятся в `/etc/config/knock-control`. В `/etc/knock-control` остаются TLS-сертификат/ключ, постоянный журнал одноразовых API nonce `api-replays.sqlite3`, резервная копия миграции и автоматически созданные `knockd.conf`/`firewall.nft`. Сгенерированные файлы не редактируйте: источником настроек служит UCI. Службы procd: `knock-control`, `knock-control-api`, подготовка правил до запуска fw4 — `knock-control-firewall`. Демон установлен как `/usr/sbin/knock-control-daemon`, чтобы не конфликтовать с обычным пакетом `knockd`.

Администратор может менять параметры через UCI, например после выдачи профиля:

```sh
# Вместо PROFILE_ID подставьте ID из knock-control list.
uci set knock-control.PROFILE_ID.idle_timeout='300'
uci commit knock-control
/etc/init.d/knock-control reload
```

Ручной `reload` проверяет настройки, обновляет конфиг демона и правила, увеличивает ревизии профилей, сбрасывает текущие разрешения и перезапускает отдельный HTTPS API. Клиентам нужно обновить статус и нажать ON. Изменение настроек через расширение по-прежнему затрагивает только его профиль. После смены интерфейса захвата выполните `/etc/init.d/knock-control restart`.

Диагностика:

```sh
/etc/init.d/knock-control status
/etc/init.d/knock-control-api status
logread -e knock-control
fw4 check
nft list chain inet fw4 knock_control_input
knock-control list
```

### Сборка OpenWrt и повторение проверки в VM

Используйте отдельный официальный SDK нужной версии и архитектуры: сборщик выбирает конфигурацию пакета в его `.config`. Исходники SDK и образ VM берутся из [официального каталога OpenWrt 25.12.5 x86/64](https://downloads.openwrt.org/releases/25.12.5/targets/x86/64/); проверьте их SHA256 по `sha256sums` из того же каталога.

```sh
cd /путь/к/распакованному/SDK
./scripts/feeds update base packages
cd /путь/к/knock
python3 scripts/build-openwrt.py --sdk /путь/к/распакованному/SDK --jobs 4 --test-tools

## Таймаут по неактивности

В обычном Linux для каждого секрета используется собственный ipset с разрешёнными IPv4. Вкл добавляет IP с `idle_timeout`. Для прежнего списка `ports` входящий и исходящий TCP-трафик установленного соединения продлевает таймаут; для именованных правил учитывается подходящий TCP/UDP/ICMP-трафик. Продление выполняется в ядре посредством `SET --exist --timeout`. Это поведение описано в [документации Netfilter](https://ipset.netfilter.org/iptables-extensions.man.html). В OpenWrt аналогичную работу выполняют наборы nftables и `update @set` с таймаутом для конкретного IPv4.

Например, при `idle_timeout=600` передача данных может идти часами. После последнего пакета защищённого соединения доступ отключится через 600 секунд. TCP keepalive и SSH keepalive тоже считаются сетевой активностью; это таймаут сетевого трафика, а не действий человека в приложении.

Knock-пакеты, неавторизованный шум, обновление статуса и изменения через API не считаются активностью защищённого сервиса. Простая проверка TCP-подключением к самому защищённому порту является активностью.

Выкл удаляет IP только из набора выбранного секрета. Если тот же IP имеет разрешение другого секрета на тот же порт, оно продолжает действовать: права складываются. При разных портах и разных секретах разрешения независимы.

Применение новых настроек сбрасывает текущие разрешения **только изменённого профиля**. Повторно нажмите Вкл. Остальные наборы сохраняются; knockd получает SIGHUP вместо остановки. При загрузке нового конфига незавершённые knock-последовательности сбрасываются, поэтому запрос, попавший ровно на обновление, может потребовать повтора.

## Отзыв и администрирование

Отозвать секрет на сервере:

```sh
sudo /usr/local/sbin/knock-control revoke PROFILE_ID
```

Это сразу убирает его разрешения, исключает последовательности из конфига и отклоняет запросы к API. Другие профили сохраняются. Вернуть отозванный ключ через клиент нельзя; выдайте новый командой `issue`.

Глобальное управление службами остаётся у администратора. Команды ниже относятся к обычному Linux; для OpenWrt используйте procd/init.d и nft из раздела выше:

```sh
sudo systemctl status knock-control.service knock-control-api.service
sudo journalctl -u knock-control.service -u knock-control-api.service -n 100
sudo /usr/local/sbin/knockd --check -c /etc/knock-control/knockd.conf
sudo iptables -S KNOCK_CONTROL
sudo iptables -S KNOCK_CONTROL_ACTIVITY
sudo ipset list
```

Для обычного Linux данные: `/etc/knock-control/settings.json`, конфиг демона `/etc/knock-control/knockd.conf`, TLS-ключ и сертификат в том же каталоге. Клиентские профили: `~/.config/knock-control/profiles.json`, права 0600. Копии выданных JSON-файлов тоже содержат секреты. В настольном режиме с помощником браузер не хранит секреты в extension storage. Хранилища HTTPS-режима описаны выше.

Если ранее была установлена версия с одним клиентским секретом и управлением по SSH, сначала остановите старый knockd, сохраните резервные копии `settings.json` и `knockd.conf`, перенесите старые файлы из этих двух путей, затем выполните новую инициализацию и выдачу. Старые клиентские JSON не импортируются в v2: секреты нужно создать на сервере заново. Старое правило `/etc/sudoers.d/knock-control` для клиентов больше не требуется.

## Протокол и защита

TOTP соответствует [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238): Base32, SHA1, 6 цифр, 30 секунд. Используются текущее и соседние окна ±30 секунд. Внутри стандарта Google Authenticator остаётся HMAC-SHA1. Код можно ввести вручную в настольном клиенте или вычислить автоматически в клиенте. Для обычного сценария ON ввод кода не нужен.

Имя двери включает ID профиля: `PROFILE_ID.open` / `PROFILE_ID.close`. Из кода, действия и IPv4 получается последовательность:

```text
SHA256(ASCII("knock-control:v1:" + door + ":" + source + ":" + code))
port[i] = base + digest[i]
source = внешний IPv4, либо "-" при отключённой привязке
```

Следует подписанное UDP-подтверждение на `base`, 60 байт:

```text
"KNC1" (4) | TOTP counter, uint64 big-endian (8) | random nonce (16) | HMAC-SHA256 (32)
HMAC key = Base32Decode(secret)
message = ASCII("knock-control:confirm:v1:") + counter + nonce + ASCII(door + ":" + source)
```

Подтверждение требуется и для Вкл, и для Выкл. Одна последовательность, случайно собранная из плотного шума, не выполняет команду. Попытки имеют фиксированный таймаут; посторонние пакеты не продлевают его. Ограничение памяти: 4096 попыток в целом, 8 на IP/дверь, 1024 использованные подписи. Переполнение не разрешает доступ. Кэш повторов knock-подтверждений находится в памяти: полный перезапуск процесса сбрасывает его. Ранее перехваченный обмен потенциально можно повторить с того же IP в ещё допустимом временном окне после перезапуска.

Управление настройками, статусом и ON/OFF в выбранном HTTPS-режиме: HTTPS `POST /v1/control`, подпись HMAC-SHA256 по ID/времени/nonce/телу. Авторизованный ID берётся из проверенного заголовка; тело не может подставить другой ID. Окно времени ±60 секунд, nonce API хранятся в SQLite и не теряются при перезапуске API. Настольный помощник сверяет SHA256 сертификата из выданного файла **до отправки авторизованного запроса**. При инициализации сервер выдаёт самоподписанный сертификат; для помощника доверие устанавливается защищённой передачей клиентского файла. В браузерном режиме нужен сертификат, доверенный браузером.

TLS-соединения ограничены 32 параллельными обработчиками с таймаутами, тело запроса — 64 КиБ, запросы ограничены по источнику. Это защита ресурсов и работа при обычном шуме, а не гарантия доступности при DDoS или потере пакетов. Расширение сообщает об отправке knocks; подтверждение фактического состояния получает отдельным запросом статуса для IP, наблюдаемого API.

Секрет находится у клиента для подписей и автоматического TOTP. Ручной код Google Authenticator не образует отдельный второй фактор при компрометации клиентского компьютера.

## Границы firewall

В обычном Linux цепочка `KNOCK_CONTROL` подключается первой в INPUT; `KNOCK_CONTROL_ACTIVITY` — первой в OUTPUT для учёта исходящей активности. Используются отдельные наборы `kc_PROFILE_ID`. Сначала разрешаются права всех активных профилей, затем блокируются общие защищённые порты. Другие таблицы и цепочки не очищаются. Вариант OpenWrt использует цепочки `knock_control_input`, `knock_control_output`, `knock_control_forward` и NAT-цепочку `knock_control_prerouting` в `inet fw4`. Для Linux добавлены собственные цепочки `KNOCK_CONTROL_FORWARD` и `KNOCK_CONTROL_NAT`; INPUT/OUTPUT/FORWARD-проверки выполняются перед штатными разрешениями established-трафика.

Эта версия управляет IPv4 TCP/UDP/ICMP, включая явные правила FORWARD/DNAT. IPv6 не поддерживается. Для контейнеров укажите действительный интерфейс/адрес и согласуйте порядок правил с их сетевым менеджером. Cloud security groups должны пропускать выбранный транспорт: UDP на базовый knock-порт для ICE, knock-диапазоны для настольного клиента, HTTPS для операций API; смотреть диапазон профиля можно в выданном файле. UDP-подтверждение должно доходить до интерфейса сервера, хотя слушающего UDP-сокета нет — используется libpcap. Конкурирующие UFW/firewalld/другие менеджеры могут изменить порядок правил: интеграцию нужно согласовать отдельно.

Старые `sequence =` и `otp =` доступны при ручном запуске knockd, но новый контроллер генерирует только `totp =`. Исходный `/etc/knockd.conf` не перезаписывается. Старый `otp =` не получает подписанное подтверждение и сохраняет строгую последовательность.

BROWSER_ENGINES=webkit PLAYWRIGHT_MODULE=/путь/к/playwright/index.mjs node tests/mobile-smoke.mjs
GECKODRIVER=/путь/к/geckodriver FIREFOX_BIN=/путь/к/firefox python3 tests/firefox-mobile-smoke.py
```

Проверены совместимость JS/Python TOTP/HMAC/последовательностей, импорт ссылки QR и настоящего PNG, сохранение профилей, ON/OFF без настройки IP, изоляция настроек, Chromium Service Worker и Firefox MV2 event page. Камерный путь проверен видеопотоком с синтетическим QR. Chromium/Firefox/WebKit запускались на Linux с мобильным размером окна: **физические Android/iPhone не проверены**. Разрешение на тестовый HTTPS-origin предварительно выдано тестовой копии расширения; тестовый сертификат принят только в тестовом браузере. Рабочие сборки проверку TLS не отключают.

CLI использует выбранный импортированный профиль либо выданный файл:

```sh
./knockd.sh open
./knockd.sh close --ask-code
./knockd.sh open --profile alice.knock.json
```

Для CLI с выданным файлом добавьте в его локальную копию `public_ip` (внешний IPv4) либо сначала импортируйте профиль и получите статус через расширение, затем используйте выбранный профиль без `--profile`.
